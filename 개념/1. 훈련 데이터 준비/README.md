# 1. 훈련 데이터 준비

LLM의 사전 훈련은 대규모 텍스트를 수집하는 것에서 끝나지 않는다. 원본 데이터를 정제하고, 토큰 ID로 변환한 뒤, 모델이 다음 토큰을 예측할 수 있는 입력과 정답 쌍으로 구성해야 한다.

## 1.1 데이터 정제

수집한 데이터가 항상 학습에 적합한 클린 데이터인 것은 아니다. 품질이 낮거나 중복된 데이터를 그대로 사용하면 모델이 잘못된 패턴을 학습하고, 편향이나 개인정보 노출 위험이 커질 수 있다. 따라서 학습 전에 다음과 같은 정제 과정이 필요하다.

- **텍스트 정규화**: 유니코드 표현, 공백, 줄바꿈, 따옴표처럼 같은 의미를 가지는 표기를 일관된 형태로 변환한다.
- **필터링**: 깨진 문서, 지나치게 짧은 문서, 광고·스팸, 의미 없는 반복 문자열, 품질이 낮은 문서를 제거한다.
- **중복 제거**: 문서 전체가 같은 정확 중복뿐 아니라 일부만 유사한 근사 중복도 제거한다. 중복 데이터가 많으면 특정 문장이 과도하게 학습되고 평가 데이터가 학습 데이터에 섞이는 데이터 누수가 발생할 수 있다.
- **개인정보 및 민감정보 처리**: 전화번호, 이메일, 계정 정보 등 학습에 불필요한 개인정보를 탐지해 삭제하거나 비식별화한다.
- **언어 및 도메인 분류**: 목표 언어와 학습 목적에 맞지 않는 문서를 제외하고, 특정 출처나 주제가 지나치게 큰 비중을 차지하지 않도록 데이터 구성을 조절한다.
- **안전성 및 라이선스 검토**: 유해 콘텐츠를 정책에 맞게 처리하고, 데이터의 저작권과 이용 조건을 확인한다.

정제 과정에서는 제거한 데이터의 수와 이유를 기록해 재현성과 추적 가능성을 확보하는 것이 좋다. 검증·테스트 데이터는 중복 제거 단계부터 학습 데이터와 분리해 데이터 누수를 방지한다.

## 1.2 토큰화와 인코딩

신경망은 문자열을 직접 계산할 수 없으므로 텍스트를 토큰으로 나눈 뒤 각 토큰을 정수 ID로 변환해야 한다.

```text
원문 문자열 → 토큰화(tokenization) → 토큰 목록 → 인코딩(encoding) → 토큰 ID 배열
```

토큰화는 어떤 단위를 기준으로 텍스트를 나누는지에 따라 크게 네 가지 방식으로 구분할 수 있다.

### 1. 단어 단위 토큰화

공백이나 문장 부호 등을 기준으로 문장을 단어 단위로 나눈다.

- 대표 도구: NLTK 등
- 장점: 결과를 사람이 이해하기 쉽고 직관적이다.
- 단점: 어휘 사전이 매우 커질 수 있으며 신조어, 오타, 합성어에서 OOV 문제가 발생한다.
- 활용: 전통적인 자연어 처리 실험이나 단어 수준 분석에 적합하다.

### 2. 형태소 단위 토큰화

단어를 어근, 조사, 어미 등 의미와 문법 기능을 가진 형태소 단위로 분석한다. 조사와 어미가 발달한 한국어의 특성을 반영할 수 있다.

- 대표 도구: KoNLPy와 그 안에서 사용하는 형태소 분석기(Okt, Komoran, Kkma, Mecab 등)
- 장점: 한국어의 문법적 구조를 비교적 세밀하게 반영한다.
- 단점: 형태소 분석 자체의 연산 비용이 들고, 분석기의 사전과 규칙에 따라 결과가 달라질 수 있다.
- 활용: 한국어 품사 분석, 키워드 추출, 전통적인 한국어 NLP 작업에 자주 사용한다.

### 3. 서브워드 단위 토큰화

자주 등장하는 문자열은 하나의 토큰으로 유지하고, 희귀 단어나 복합어는 더 작은 단위로 분해한다. 현대 LLM에서 가장 널리 사용되는 방식이다.

- 대표 알고리즘: BPE, Byte-level BPE, WordPiece, Unigram
- 장점: 단어 단위 방식보다 어휘 사전의 크기를 제어하기 쉽고, 희귀 단어도 기존 서브워드의 조합으로 표현할 수 있다.
- 주의: 바이트 기반이 아닌 제한된 문자 집합의 서브워드 토크나이저는 미등록 문자를 별도 미지 토큰으로 처리할 가능성이 있으므로 구현에 따라 OOV 여부가 달라진다.

### 4. 문자 또는 바이트 단위 토큰화

텍스트를 알파벳, 한글 음절, 유니코드 문자 또는 UTF-8 바이트처럼 매우 작은 단위로 나눈다.

- 장점: 바이트 단위 방식은 모든 입력을 표현할 수 있어 OOV가 발생하지 않는다.
- 단점: 같은 문장을 표현하는 토큰 수가 늘어나 시퀀스가 길어지고 연산량이 증가할 수 있다.

### OOV란?

**OOV(Out Of Vocabulary)**는 입력에 등장한 단어나 문자가 토크나이저의 어휘 사전에 포함되어 있지 않은 상태를 뜻한다. 신조어, 오타, 맞춤법 오류, 고유명사 등에서 자주 발생한다. 전통적인 단어 토크나이저는 이를 `[UNK]` 같은 미지 토큰으로 바꾸지만, 서브워드 또는 바이트 기반 토크나이저는 입력을 더 작은 단위로 분해해 문제를 크게 줄인다.

## 1.3 한국어와 LLM 토크나이저

한국어는 조사와 어미가 결합하고 하나의 음절이 여러 UTF-8 바이트로 표현되기 때문에 토크나이저에 따라 같은 문장의 토큰 수가 크게 달라질 수 있다. 토큰 수가 많아지면 동일한 문맥을 처리하는 비용과 메모리 사용량도 증가한다.

### tiktoken과 GPT 계열 모델

`tiktoken`은 OpenAI 모델에서 사용하는 빠른 BPE 계열 토크나이저 라이브러리다. GPT-4o 계열에서 사용하는 `o200k_base` 인코딩은 이전 인코딩보다 큰 어휘 사전을 사용하며, 다국어 텍스트를 더 효율적으로 표현하도록 개선됐다. 다만 실제 한국어 토큰 수는 문장 구성에 따라 달라지므로 모델을 선택할 때 샘플 데이터로 직접 측정해야 한다.

### EXAONE

EXAONE은 LG AI Research가 개발한 한영 중심의 대규모 언어 모델 계열이다. 공개된 EXAONE 모델은 Hugging Face에서 모델 가중치와 사용 조건을 확인하고 자체 인프라에 배포할 수 있다.

- 자체 서버에서 추론하면 프롬프트를 외부 상용 API로 보내지 않는 구성을 만들 수 있어 민감 데이터 처리에 유리하다.
- 그렇더라도 서버 로그, 접근 제어, 저장 정책, 모델 라이선스와 개인정보 처리 요건은 별도로 검토해야 한다.
- 토큰화 방식과 형태소 수준의 분절 결과는 모델 및 공개된 토크나이저 버전별로 확인해야 한다. 한국어 모델이라고 해서 반드시 별도의 형태소 분석기를 사용하는 것은 아니다.

**Hugging Face**는 모델, 데이터셋, 토크나이저와 관련 도구를 공유하고 사용할 수 있는 오픈소스 AI 플랫폼이자 커뮤니티다.

## 1.4 데이터셋과 데이터 로더 정의

전체 학습 데이터는 한 번에 메모리나 GPU에 올리기 어렵기 때문에 일정한 길이의 청크와 미니배치로 나누어 공급한다. PyTorch에서는 보통 `torch.utils.data.Dataset`과 `torch.utils.data.DataLoader`를 사용한다.

### 다음 토큰 예측

일반적인 자기회귀 LLM 사전 훈련의 목표는 **다음 토큰 예측(Next Token Prediction, Causal Language Modeling)**이다. 연속된 토큰 ID를 한 칸씩 이동해 입력과 정답을 만든다.

```text
전체 토큰:  [BOS, 오늘, 날씨, 는, 맑다, EOS]
input_ids: [BOS, 오늘, 날씨, 는, 맑다]
labels:    [오늘, 날씨, 는, 맑다, EOS]
```

- `input_ids`: 현재 위치까지 모델이 입력으로 받는 토큰 ID 배열
- `labels` 또는 `target_ids`: 각 위치에서 모델이 예측해야 하는 다음 토큰 ID 배열
- `max_length`: 하나의 학습 청크에 포함할 최대 토큰 수

코드에서는 길이가 `max_length + 1`인 구간을 선택한 뒤 앞부분을 입력, 뒷부분을 정답으로 사용할 수 있다.

```python
chunk = token_ids[i : i + max_length + 1]
input_ids = chunk[:-1]
target_ids = chunk[1:]
```

입력과 정답이 같은 문장을 재현하도록 학습하는 것이 아니라, 각 위치의 입력 문맥을 바탕으로 **바로 다음 토큰의 확률을 높이는 방향**으로 손실을 최소화한다. Transformer의 causal attention mask는 각 위치가 미래의 정답 토큰을 미리 보지 못하게 막는다.

### Dataset 단계

`Dataset`은 토큰 ID 배열에서 학습에 사용할 입력-정답 청크를 생성하고 인덱스로 접근할 수 있게 한다.

- 청크 길이와 이동 간격(stride)을 결정한다.
- 문서 경계를 넘어서 청크를 연결할지, 문서 사이에 EOS 토큰을 넣을지 결정한다.
- 데이터가 매우 크면 전체를 메모리에 올리지 않고 파일 스트리밍, 메모리 매핑 또는 샤딩을 사용한다.
- 고정 길이 패킹을 사용하면 남는 공간을 줄여 GPU 사용 효율을 높일 수 있다.

### DataLoader 단계

`DataLoader`는 `Dataset`에서 만든 샘플을 모델이 한 번에 처리할 미니배치로 묶어 공급한다.

- **`batch_size`**: 한 번의 연산에 포함할 청크 수다. 메모리 한계를 넘는 경우 그래디언트 누적을 함께 사용할 수 있다.
- **`shuffle=True`**: 에포크마다 샘플 순서를 섞어 특정 문서 순서에 대한 편향을 줄인다. 분산 학습에서는 `DistributedSampler` 등으로 각 장치가 서로 다른 샘플을 받도록 구성한다.
- **`collate_fn`**: 길이가 다른 샘플을 패딩하고 `attention_mask`를 생성한다. 모든 청크를 고정 길이로 패킹했다면 단순히 텐서를 쌓는 것으로 충분할 수 있다.
- **`num_workers`**: 여러 CPU 프로세스가 다음 배치를 병렬로 준비해 GPU의 데이터 대기 시간을 줄인다.
- **`pin_memory`와 prefetch 설정**: CPU에서 GPU로 데이터를 전송하고 다음 배치를 미리 준비하는 비용을 줄이는 데 사용할 수 있다.

패딩 토큰은 실제 정답이 아니므로 보통 해당 위치의 label을 `-100`으로 설정해 손실 계산에서 제외한다.

## 1.5 전체 처리 흐름

```text
원본 데이터 수집
    ↓
품질 정제·중복 제거·개인정보 및 라이선스 검토
    ↓
학습/검증/테스트 데이터 분리
    ↓
토큰화 및 정수 ID 인코딩
    ↓
고정 길이 청크 또는 패킹된 시퀀스 생성
    ↓
input_ids와 한 칸 이동한 labels 구성
    ↓
DataLoader가 미니배치로 모델에 공급
    ↓
다음 토큰 예측 손실 계산 및 모델 파라미터 업데이트
```

훈련 데이터의 품질, 토크나이저의 효율, 청크 구성 방식은 모델의 성능뿐 아니라 학습 비용과 안전성에도 직접적인 영향을 준다.
